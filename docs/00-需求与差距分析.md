3. **AI-Native 工程实践**：持续探索并激进尝试最新的 AI 开发范式，并落地到工业场景或内部工具链中。

1. **编程基础**：熟练掌握 Python 或 TypeScript（至少其一），能写清晰可维护的代码；理解异步、事件驱动等概念；具备 API 集成与调试能力。

4. **产品思维与快速原型**：能从用户视角定义问题，快速理解工业场景的粗糙需求；能独立完成功能拆解、原型绘制，并**落地**为可演示的 MVP。
5. **模块化设计能力**：对 Agent 应用做合理模块化（规划 / 执行 / 记忆 / 工具分离），具备接口抽象意识，支持组件可**替换与测试**。
6. **AI-Native 工作方式**：激进拥抱新 AI 工具与范式，接受快速试错（哪怕失败）；乐于分享「如何用 AI 把某件事效率提升 10 倍」，带动团队研发效率。
7. **学习与韧性**：适应短期工厂驻场或产线调研，愿意在嘈杂环境中理解工人/工程师的真实操作习惯；保持好奇心；**能快速试错并提炼经验**。

### 加分项

1. 用过 **LangChain / OpenAI / Pi** 等 Agent 编排框架，并**理解其设计取舍**。
2. 既写过 Python 后端（**FastAPI**）也写过 TS 前端（**React/Vue**），有全栈项目 0→1 搭建经历。
3. 有工业领域软件开发经验（**MES 插件、设备数据采集、维修工单系统**等）。

## 6. 项目提案

### 推荐选题：**产线良率异常根因分析 Agent（Line RCA Agent）**

一句话：*把 AOI/传感器看到的「异常」，翻译成工程师能立刻执行的「根因 + 处置 + 工单」。*

选它的四个理由：

1. **正中 JD 职责 1 的第三场景**「产线异常分析」，且是三个场景里技术含量最高、最难被替代的。
2. **最大化你的存量优势**：RCA、告警降噪、MTTR、全链路可观测——这些是你 15 年攒下的东西，别人抄不走。你的差异化标签可以是「**懂可观测的 Agent 工程师**」。
3. **天然覆盖加分项 3**：设备数据采集（模拟产线时序 + 缺陷记录）、维修工单系统（工单 CRUD + 派单/闭环）都要真实实现。
4. **可验证、可量化**：良率、误报率、平均定位时间（MTTR 同构指标）、根因 Top-K 命中率，全都能做成可复现的评测数字——这是你评测驱动的强项，也是「数据飞轮」叙事。

### 三个子场景 ↔ JD 职责 1 的映射

| JD 场景 | 项目里的形态 |
|---|---|
| 产线异常分析 | Agent 收到「某批次良率突降」→ Plan-and-Execute 分解 → 并行拉取 AOI 缺陷分布 / 设备遥测 / 工艺参数 / 历史相似案例 → 输出根因排序 + 证据链 + 建议处置 |
| 工艺流程辅助 | 基于 SOP / 工艺参数手册 / 历史调参记录的 RAG，回答「某工序参数该怎么调」，并给出参数建议与依据条款 |
| 工业知识问答 | 设备手册、报警码、维修知识库的统一问答入口（把报警码映射到处置动作） |

### Agent 模块划分（直接对应 JD 要求 5 的「规划/执行/记忆/工具分离」）

```
planner/      Plan-and-Execute 的规划器（可替换：LangGraph 版 / 自研版）
executor/     ReAct 执行器（Thought→Action→Observation，全轨迹留痕）
memory/       短期会话记忆 + 长期案例库（向量 + 结构化）
tools/        协议化工具层（MCP 封装）：遥测查询 / 缺陷分布 / SPC / SOP 检索 / 工单 CRUD / 相似案例
guardrails/   三层防幻觉（沿用你 HS Code 项目的方法论）
observability/ OpenTelemetry + Agent 轨迹追踪（差异化护城河）
eval/         评测集 + 对抗样本 + 回归 CI
providers/    LLM 后端可替换（DeepSeek / OpenAI 兼容 / Ollama 本地）
```

要求 5 的「支持组件可替换与测试」是**必须显式证明**的：同一套 Agent，能在 `LangGraph 编排` 与 `自研编排` 之间一键切换，且有对照测试。这也顺手命中加分项 1 的「理解设计取舍」——再配一篇 `docs/adr/` 选型对比（LangGraph vs 自研 vs Pi）。

### 数据从哪来（已核实，含一处关键修正）

不编数据，用公开工业数据集：

- **SECOM（UCI 半导体制造数据集，CC BY 4.0，DOI 10.24432/C54305）** —— 已核实：**1567 样本 × 591 个传感器特征**，标签只有「良/不良」且**仅 104 条不良（6.6%，极度不平衡）**，**含大量 NaN 缺失值**，另附时间戳。它本质是**特征选择 / 因果发现**基准，**不提供根因标注**。
- ⚠️ **修正：因此「根因 Top-1/Top-3 命中率」不能直接从 SECOM 标签算出。** 正确做法是把 SECOM 当作**真实工况基线**，在其传感器信号上做**受控故障注入**（漂移 / 阶跃 / 尖峰 / 相关性破坏 / 传感器卡死）——注入时我们就知道真实根因，于是得到**带根因真值的评测集**。这正是工业 RCA 领域的标准做法（故障注入基准）。
- **MVTec AD**（二期可选，默认不做）：许可是 **CC BY-NC-SA 4.0（非商用）**，公开仓库**不得打包其图像**，只允许脚本拉取用于本地演示。
- **设备遥测 / 工单数据**：按 OPC UA / MQTT 语义由 `scripts/simulate_plc.py` 生成，README 明确标注 *simulated*。

> 这套组合的好处是两头都占：既有**真实工业数据的脏**（缺失值、极不平衡、工况漂移），又有**可控的根因真值**（注入）。面试时「数据真实性」和「评测可复现」可以分开讲清楚。
