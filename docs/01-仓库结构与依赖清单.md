## 3. 模块边界与依赖方向

这是 JD 要求 5「模块化设计 + 接口抽象 + 组件可替换」的**可验证证明**，不是嘴上说说：

```text
apps/web  ──HTTP/SSE──▶  apps/api  ──▶  packages/agent-core  ──▶  (无仓内依赖)
   TS/React                FastAPI         纯 Python 内核
```

三条**由 CI 强制**的规则：

| 规则 | 强制方式 |
|---|---|
| `agent-core` **不得** import fastapi / sqlalchemy / anyio-server | `import-linter` 契约测试，CI 失败即红 |
| `agent-core` 访问数据库必须经 `Protocol`（实现放在 `apps/api/repositories/`） | 同一契约测试 + 单元测试用内存实现 |
| `web` 不得硬编码后端字段名，类型来自 `shared/events.ts` 单一来源 | `tsc --noEmit` + 契约快照测试 |

**为什么值得这么做**：面试时可以直接把 `import-linter` 的失败截图甩出来——「我不仅做了分层，我还让 CI 保证它不被破坏」。

## 4. 关键接口草案（示意，非实现）

`packages/agent-core/src/line_rca_agent/contracts.py` 里将是这些 Protocol：

```python
class Planner(Protocol):
    async def plan(self, goal: Goal, ctx: Context) -> Plan: ...


class Executor(Protocol):
    async def step(self, plan: Plan, state: State) -> StepResult: ...


class Tool(Protocol):
    name: str
    description: str
    input_schema: dict  # JSON Schema，MCP 同源

    async def run(self, args: dict) -> ToolResult: ...


class Memory(Protocol):
    async def write(self, item: MemoryItem) -> None: ...
    async def recall(self, query: str, k: int) -> list[MemoryItem]: ...


class LLMProvider(Protocol):
    async def complete(self, msgs: list[Msg], **kw) -> Completion: ...
    def stream(self, msgs: list[Msg], **kw) -> AsyncIterator[Delta]: ...


class TraceSink(Protocol):
    async def emit(self, event: TraceEvent) -> None: ...
```

**轨迹事件契约（前端可视化的命脉）**——统一信封，带 `schemaVersion`：

```text
{ schemaVersion: "1", seq: 12, ts: "...", runId: "...", type: "tool.called", payload: {...} }
```

事件类型：`run.started` / `plan.created` / `step.started` / `thought` / `tool.called` / `tool.result` / `guardrail.blocked` / `answer` / `run.finished` / `run.failed`。

前端「推理轨迹时间轴」直接消费这一串事件，**不猜后端结构**。这也让「轨迹导出为报告」变成纯前端能力。

### 6.5 明确**不引入**的依赖及理由

| 不引入 | 理由（也是面试可讲的取舍） |
|---|---|
| Celery / Redis / RabbitMQ | 单机规模用 FastAPI `BackgroundTasks` + APScheduler 足够；引入消息队列会多两个运维组件，收益为负。这个取舍写进 ADR-0003 |
| ChromaDB / FAISS | 长期案例记忆统一走 **pgvector**，少一个存储组件、少一次数据同步；FAISS 适合纯本地场景，本项目的检索要跟关系数据 join |
| LangChain 全家桶 | 只取 `langchain-core` 的最小接口面。你在 hs-code-classifier 里已经踩过版本地狱，这次把依赖面收窄写进 ADR-0001 |
| Redux / MobX | TanStack Query 管服务端状态 + zustand 管少量 UI 状态，够了 |
| Ant Design / MUI | 工业看板需要高度定制，Tailwind + shadcn 风格组件更可控，也更能体现"UI 做极致" |
| Recharts | 缺陷热力图与良率瀑布的数据量偏大，ECharts 的 canvas 渲染与交互更合适；只留一个图表库 |
| 前端 codegen（openapi-typescript） | 初期事件模型手写 + 契约快照测试，避免 codegen 拖慢迭代；等接口稳定再评估 |

### 11.1 两条会咬人的本地开发约束（本轮实测）

1. **npm 缓存必须放在仓库内**：npm 默认缓存目录是 `AppData\Local\npm-cache`（仓库外），会被文件沙箱直接拒绝，连 `npm view` 都会失败。项目内固定 `npm_config_cache` 指向仓库内目录即可（已验证）。
2. **前端 `build` / `test` / `e2e` 必须提权运行**：Vite 8 在 Windows 解析真实路径时会 `exec('net use')`，受限沙箱禁止管道 stdio → `spawn EPERM`。已实测 `spawn(..., {stdio:'ignore'})` 正常、`exec` 一律 EPERM，且摘掉 Tailwind 插件后仍失败，确认与依赖版本无关。`tsc` / `eslint` 则**不需要**提权。
   → 这条必须写进 README 的「本地开发」一节。
3. **`pip` 在本机不可用，必须用 `uv`**：pip 在它自己的 `pip-unpack-*` / `pip-target-*` 目录里做后续操作会被拒绝（`Errno 13` / `WinError 5`）。uv 已通过「Node 下载 wheel → Python `zipfile` 解压」引导完成，之后一切 Python 依赖走 uv。详见 [02-M1兼容性验证报告.md](02-M1兼容性验证报告.md) §9。

## 13. 环境勘查结论（本轮实测，含两个会阻塞计划的发现）

### 13.1 网络：github.com 没被封，是 hosts 把它指向了「时好时坏」的本地加速器

实测结果（Node 直连，绕过 hosts 用真实 IP）：

| 目标 | 结果 |
|---|---|
| pypi.org / registry.npmjs.org / npmmirror / mirrors.aliyun.com / baidu.com | ✅ HTTP 200（47–766 ms） |
| **github.com 真实 IP**（`140.82.112.3` / `20.205.243.166`） | ✅ TCP OPEN + **TLS 通过且是真证书**（`Sectigo Public Server Authentication CA DV E36`） |
| **同上，模拟 git 请求**（`info/refs?service=git-upload-pack`） | ✅ **HTTP 200 + git smart-http 识别成功**，`authorized=true` |
| `20.205.243.166:22`（GitHub SSH 22 端口） | ✅ TCP OPEN |
| **`github.com` 走系统解析（hosts → 127.0.0.1 → 加速器）** | ⚠️ **不稳定**：同一命令一次 21 s 超时失败，20 分钟后同样命令**成功**（`git ls-remote` 正常返回 refs） |
| api.github.com（经加速器 MITM） | ✅ 200 / 424 ms，但证书是 `CN=SteamTools Certificate` |
| ssh.github.com:443 | ✅ 可达，SSH 服务握手正常（`Permission denied (publickey)`） |

**结论修正**：`github.com` **并没有被链路封锁**，真实 IP 直连稳定可用。问题出在
`C:\Windows\System32\drivers\etc\hosts` 被 **Watt Toolkit（原 Steam++）** 改写，把 `github.com`、`api.github.com`、`raw.githubusercontent.com`、`huggingface.co`、`vercel.app` 等指向 `127.0.0.1`，再由提权进程 **`Steam++.Accelerator`（PID 30228，监听 `0.0.0.0:80/443`）** 做 MITM 转发。它转发 `github.com` 时**时通时断**，所以你的推送是「有时能推、有时卡死 21 秒」。

这也解释了两件事：你全局设的 `git config http.sslverify false`（Node/curl/Git 不认 SteamTools 那套根证书），以及 8 月 26 日之后的提交中断。

### 13.2 修法（推荐做法只需要改 hosts 一行）

| 方案 | 动作 | 权限 | 效果 |
|---|---|---|---|
| **C-1（推荐）** | 删掉 hosts 里的 `127.0.0.1 github.com` 这一行 | 需管理员 | git 走 DNS → 真实 IP → **真证书直连，稳定**；且**立刻修好你所有旧仓库的推送**。建议同时在 Watt Toolkit 里关掉 `github.com` 的 hosts 改写，否则它重启会写回来 |
| C-2 | 把 `127.0.0.1 github.com` 换成 `140.82.112.3 github.com` | 需管理员 | 同样直连，但 GitHub IP 会变，长期不如 C-1 |
| A（不需要管理员） | PAT → 我用 API 建仓 + 注册你已有的 ed25519 公钥；你在 `~/.ssh/config` 加一段指向 `ssh.github.com:443` | 无需管理员 | SSH/443 已实测可达，完全绕开 hosts |
| — | 重启 Watt Toolkit / 重勾 GitHub 加速 | 无需管理员 | 只能缓解，过一阵还会复发 |

**补充证据**：我导出 SteamTools 根证书给 Node 用（`NODE_EXTRA_CA_CERTS`）后，`GET api.github.com/users/xiaohe9` 返回 **HTTP 200、`login=xiaohe9`、`public_repos=18`**，与你的账号完全一致——所以走 API 建仓/注册公钥这条路是通的。证书已导出到 `_tools/steamtools-ca.pem`（有效期至 2027-05-19，随 `_tools/` 一起 gitignore）。

### 13.3 顺带发现

- **`~/.ssh/id_ed25519`（注释 `pycharm`）尚未注册到 GitHub**；`~/.ssh/config` 里只有一台阿里云 ECS（`okki-server` / `39.108.85.252`），可作**备用中继**。
- **不要整体清空 hosts 的加速器条目**：`raw.githubusercontent.com`、`huggingface.co`、`objects.githubusercontent.com` 这些直连通常不通，还需要加速器。只处理 `github.com` 一行即可。
- `_tools/known_hosts` 写不进去是**文件沙箱**导致的（workspace-write 不允许写 `~/.ssh/`），不是权限问题——所以那段 SSH config 得你来加，或授权我提权执行一次。
