# 04 · M2 数据层验证报告

> 目标：把 API 从「罐头字典」接到真实数据库，让 Agent 的工具变成真实 SQL，并让一次分析真的产生产线可执行的动作。
> 结论：**迁移建表、数据播种、5 个真实工具、工单写入全部跑通；经 nginx 的 15 项端到端检查全过。**

---

## 1. 交付内容

### 持久化

四张表，由 **alembic 迁移**建出（不是 `create_all`），迁移文件在
`apps/api/src/line_rca_api/migrations/versions/0001_initial_schema.py`：

| 表 | 用途 |
|---|---|
| `batches` | 批次、投产数、不良数；不良率是**派生值**，不重复存储 |
| `defect_records` | 按「批次 × 工位 × 缺陷类型」聚合的 AOI 结果 |
| `telemetry_samples` | 设备读数，**同时存基线** |
| `work_orders` | 维修工单，含回指 Agent 运行的 `run_id` |

两个设计选择值得说明：

- **遥测同时存基线**。根因结论必须说「0.199 mm vs 基线 0.06 mm」，如果基线是事后从别处推的，历史就被悄悄改写了。
- **工单带 `run_id`**。这条让「推荐」在事后仍可审计：工单能指回产生它的那次推理轨迹。

### 模拟数据集（确定性）

固定随机种子，保证 demo、测试、截图看到的是同一组数字：

| 批次 | 不良率 |
|---|---|
| B-2036 … B-2039 | 1.90% – 2.63% |
| B-2040 | 4.00% |
| **B-2041** | **40.98%** |

而 B-2041 的 486 个不良里 **372 个是镀膜工位的划伤**，同期镀膜振动 0.199 mm（基线 0.06）。数据被刻意造成「有明确答案、但需要两步才能确认」的形状。

### 真实工具（4 读 1 写）

`query_defects` / `query_telemetry` / `find_similar_cases` / `list_work_orders` / **`create_work_order`**。

工具层依赖 repository **Protocol**，所以工具本身可以用内存假件单测（无需数据库），SQL 实现另有集成测试。`create_work_order` 闭包捕获当前 `run_id`，写进工单。

### 编排

compose 新增一次性 `migrate` 服务，`api` 等它 `service_completed_successfully` 再启动——**`docker compose up` 仍然是一条命令**，而迁移与播种不被塞进 API 进程里偷偷执行。

### 健康检查的诚实拆分

- `GET /live` —— 只证明进程活着，不碰数据库；
- `GET /ready` —— 真的执行 `select 1`；
- `GET /health` —— 自描述当前装配，**需要数据库**。

这样编排器能区分「进程死了」和「依赖死了」，而不是把两者混成一个失败。

## 3. 本轮撞到并修掉的四个问题

### 3.1 `greenlet` 缺失

```
ImportError: The SQLAlchemy asyncio module requires that the Python 'greenlet' library is installed
```
修法不是手动加一个包，而是把依赖声明成自解释的形式：`sqlalchemy[asyncio]==2.1.4`。

### 3.2 `asyncio.run` 撞上 pytest-asyncio 的事件循环

测试夹具原本在进程内建表，与 pytest-asyncio 的循环冲突。修法不是绕过循环，而是**让测试调用与生产完全相同的引导命令**：

```
python -m line_rca_api.db.bootstrap --reset
```

作为子进程执行，天然没有循环纠缠，而且测试验证的就是生产路径。

### 3.3 我自己写的检查出现假阳性：`/ready` 返回的是 SPA 的 HTML

```
ok  GET /ready (database reachable) — <!doctype html>...
```

nginx 只代理了 `/api/` 和 `/health`，`/live`、`/ready` 落到了 SPA 回落路由，于是**返回 200 + HTML**，而我的检查只断言了状态码。两处都修了：

- nginx 用一条正则 location 覆盖全部运维端点；
- 检查改为**断言响应体**（`{"status":"ready"}`），因为「没被代理的服务会假装健康」这类错误，状态码永远看不出来。

这类假阳性是自动化验证里最危险的一种：它让报告变绿而问题仍在。

### 3.4 同一个 registry 有两种顺序

`/health` 用 `names()`（已排序），`/api/tools` 用 `schemas()`（注册顺序）。这不只是显示不一致——**工具目录是请求前缀的一部分**，注册顺序泄漏进去会让提示词依赖 import 顺序。已在源头修正并补了测试。

## 4. 验证边界（诚实声明）

**未做**：

- **MQTT 采集尚未接入**。broker 已在运行、`telemetry_samples.source` 字段已就位，但还没有发布端与订阅端；
- **向量记忆未做**。`find_similar_cases` 目前是**词法匹配**（`ILIKE`），代码里明确标注为向量召回的占位实现；
- **SECOM 数据集未接入**。它属于评测链路，与当前的模拟运行数据是两回事；
- **前端尚未消费新端点**。`/api/batches`、`/api/workorders` 已可用，但 UI 仍只展示轨迹与结论。

**已知代码内标注的限制**：工单号的生成用「当天计数 + 1」，并发创建会竞争。主键会让它变成插入失败而不是静默重复，真实部署应换成数据库序列——代码里写明了。
