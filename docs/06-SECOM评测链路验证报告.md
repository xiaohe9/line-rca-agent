# 06 · SECOM 评测链路验证报告

> 目标：让「评测驱动」从一句话变成可复现的数字与 CI 门禁——这也是这份简历里最有说服力的能力。
> 结论：**注入 → 诊断 → 指标 → 基线 → 回归门禁全部跑通。但这一轮真正的产出不是那组数字，而是评测把我自己写的诊断器证伪了六次。**

---

## 1. 交付内容

| 组件 | 说明 |
|---|---|
| `scripts/fetch_secom.py` | 下载 SECOM（CC BY 4.0）到 `eval/datasets/`，**不入库**，附 SHA256 与出处 |
| `eval/secom.py` | 加载器 + 健康窗口筛选（完整列 + 非恒定列） |
| `eval/injection.py` | 受控故障注入：drift / step / spike / dead / decorrelate，注入即真值 |
| `eval/diagnoser.py` | 确定性基线诊断器 + **阈值标定** |
| `eval/run_eval.py` | 评测 CLI：报告 / 记录基线 / 回归检查 |
| `eval/baselines/baseline.json` | 已记录的基线（含阈值来源与每类故障的分解） |
| `eval/tests/test_eval.py` | 13 个测试，**不依赖数据集**（合成参考），CI 无需联网 |
| CI 作业 `evaluation` | 拉数据 → 评测 → 与基线比对，**指标回退即红** |

### 为什么必须做故障注入

SECOM 的标签只有「良/不良」，**没有根因**。所以根因是被**造出来**的：取一段真实健康窗口当参考，给某个传感器注入一个有名字、有位置的扰动，真值就是注入的东西。这也是工业 RCA 基准的通行做法——反过来让模型去猜没有依据的根因，得到的数字无法检验。

## 3. 评测把我证伪了六次

这一节是这份报告里最该读的部分。第一版诊断器跑出来是：**假阳性 100%、step/drift/spike 的 Top-1 全为 0%**。

### 3.1 用原始离散度做了标准误

窗内中位数（60 行）与参考中位数（200 行）之差的标准化，我一开始除以了**总体离散度**。正确除数是**中位数的标准误**（`1.253σ/√n`，两个中位数各有一份）。不修的话，普通抽样噪声就被报成 6σ 的异常。

### 3.2 400 个传感器上的多重比较没有校正

阈值本来是我拍的一个 6.0。但有 400 个传感器时，**400 个零假设统计量的最大值本来就在 3.5 上下**，6.0 会稳定产生假阳性。

修法不是换个更大的数，而是**标定**：在**独立种子**的对照窗上测出零分布，把阈值设在目标假阳性分位点上，并把「标定得来」写进基线文件。阈值从此有出处。

### 3.3 「对照」根本不成立

标定后假阳性仍有 100%，而且零假设峰值高到 91。查下去才意识到：**SECOM 的行是按时间排序的**，产线在数月里会漂移。我拿文件开头 200 行当参考、中间 60 行当待查窗——**那是两个不同的过程**。

正确的做法也更贴近现实：**用紧邻之前的窗口做参考**（现场就是这么比的），漂移被共享掉。零假设立刻合理了。

### 3.4 重尾数据上 MAD 低估尺度

即使改成相邻窗口，零假设峰值仍到 52。原因是 SECOM 的传感器**重尾**，而 MAD 在重尾分布上会**低估**尺度——标准误被算小，z 被整体放大一个数量级。

改用样本标准差：它同样被尾部放大，**但方向是安全的**——这个基线宁愿漏报也不愿误报。

### 3.5 「卡死」用离散度比例判据会误触发

我用「窗内离散度 < 0.25 × 参考离散度」判定传感器卡死。但一个取值大量重复的传感器，在 60 行窗里 MAD **恰好等于 0**，于是健康窗口被误判为卡死，阈值被顶到上限。

改成**「窗内极差为 0 而参考有变化」**——卡死就是字面意义上的不动。

### 3.6 近常数列上的方差比是数值噪声

我原先用对数方差比做「离散度变化」证据。对离散度只有自身量级 0.03% 的传感器，方差比可以轻易到 1000 倍——那不是信号，是浮点噪声。

两处修正：把常数传感器门槛从 `1e-6` 收紧到 `1e-3`；并把**离散度检验换成离群点计数**（超出参考 8 个稳健 sigma 的点数），因为「卡死」是规则不是假设检验，而「尖峰」的形状本来就是**一串**离群点——单个 8σ 点在一台重尾产线上什么都说明不了，实测正是它把阈值顶到了 59。

## 4. 验证边界（诚实声明）

- **基线很弱**（Top-1 32.7%）。它的意义是给出一个可超越的目标，不是给出一个能用的诊断器；
- **`decorrelate` 是明确的盲区**：均值、离散度都不变，只丢失与全线的相关性。代码里以 `BASELINE_BLIND_SPOTS` 显式声明，评测单独报告它——**这正是「能规划一次对比的 Agent」值得存在的地方**；
- **评测限制在 400 行连续数据内**。因为 SECOM 「终检合格」不等于「过程正常」：全量数据里存在真实的工况切换，把跨越切换的窗口当对照，本身就是错的。扩到全量需要先做变点检测，属于后续工作；
- **LLM/Agent 还没有参与这份评测**。这一轮交付的是**基线与评测装置**——必须先有基线，才谈得上说 Agent 更好。

## 5. 复现

```powershell
uv run python scripts/fetch_secom.py          # 取数据（不入库）
uv run python -m eval.run_eval                # 报告，阈值现场标定
uv run python -m eval.run_eval --check eval/baselines/baseline.json   # 回归检查
uv run pytest eval                            # 13 个测试，不需要数据集
```
