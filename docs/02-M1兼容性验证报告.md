# 02 · M1 兼容性验证报告

> 目的：在写项目代码之前，验证 `TypeScript 7 + Vite 8 + ESLint 10 + Tailwind 4 + React 19` 这套全新大版本组合能否协同工作。
> 方法：在 `_spike/web-compat/` 建一个一次性最小工程（React + ECharts + motion + Tailwind），跑 `typecheck / lint / test / build` 四关。
> 结论：**4/4 通过，但必须把 TypeScript 从 7.0.2 回退到 6.0.3**，并发现一条影响全流程的沙箱约束。

## 2. 唯一的不兼容：TypeScript 7.0.2 → 回退 6.0.3

安装时立即失败（8 秒内暴露，这正是把验证放最前面的价值）：

```
npm error ERESOLVE unable to resolve dependency tree
npm error Found: typescript@7.0.2
npm error Could not resolve dependency:
npm error peer typescript@">=4.8.4 <6.1.0" from typescript-eslint@8.71.2
```

**证据链**：

| 事实 | 来源 |
|---|---|
| typescript `latest` = **7.0.2**；6.x 最新 = **6.0.3**；5.x 最新 = 5.9.3 | `npm view typescript versions` |
| typescript-eslint `latest` = 8.71.2，peer 为 `typescript >=4.8.4 <6.1.0` | `npm view typescript-eslint peerDependencies` |
| **连 canary（8.71.3-alpha.4）也仍是 `<6.1.0`** | `npm view typescript-eslint@canary peerDependencies` |
| TS 7 通过 `optionalDependencies` 分发 `@typescript/typescript-win32-x64` 等**平台二进制** → 即原生编译器重写版 | `npm view typescript@7.0.2 optionalDependencies` |
| typescript-eslint 支持 `eslint ^10.0.0` | 同上 |

**判定**：TS 7 是原生（Go）编译器重写，基于 JS 编译器 API 的 typescript-eslint 无法在短期内支持。因此：

> **决定：项目锁定 `typescript@6.0.3`**，其余全部用最新大版本。待 typescript-eslint 的 peer 范围放开 TS 7 后再单独升级（届时重跑本报告的验证矩阵）。

## 4. 新发现的环境约束（影响整个项目流程）

**`vite build` 与 `vitest` 在 DSH 默认沙箱（workspace-write）下无法运行。**

根因是 Vite 8 在 Windows 上解析真实路径时会执行 `child_process`，而受限模式禁止管道 stdio：

```
exec('net use')                  [pipe]  -> THREW EPERM
execFile('cmd', ['/c','echo'])   [pipe]  -> THREW EPERM
spawn(..., { stdio: 'ignore' })          -> OK exit 0
```

失败位置固定为 `bundleConfigFile` → `windowsSafeRealPathSync`（Vite 8 用 `rolldown` 打包配置文件时触发）。
为排除误判，我把 Tailwind 插件摘掉后重跑，**vitest 与 build 仍在同一位置失败** → 说明与 Tailwind 4 无关，纯属沙箱限制。

**处理方式**：本项目所有前端 `build` / `test` / `e2e` 命令都需要提权执行（`danger-full-access`）。这条要写进 README 的"本地开发"一节，否则别人克隆下来会一头雾水。

## 9. 新发现：pip 在本环境不可用，uv 必须「绕过 pip」引导

### 9.1 现象

`pip install` 必然失败，且失败点不固定：

```
Errno 13 Permission denied: '...\pip-unpack-xxx\fastapi-0.143.0-py3-none-any.whl'
[WinError 5] 拒绝访问: '...\pip-target-xxx\lib'
```

### 9.2 已排除的原因（逐条做了实验）

| 假设 | 实验 | 结论 |
|---|---|---|
| 临时目录位置不对 | 把 `TEMP`/`TMP` 指到工作区内再装 | ❌ 仍失败 |
| 网络问题 | Node 直连 pypi.org / 清华镜像 | ❌ 均 200，pip 也确实下载成功 |
| wheel 文件损坏 | 用 Node 下载同一 wheel，再让 Python `zipfile` 打开 | ❌ **打开正常，47 个条目** |
| 只能读本地 wheel？ | `pip install --no-index <本地 wheel>` | ❌ **不再报 Errno 13**，只因缺依赖失败 |
| 通用的「临时文件+重命名」被禁 | 工作区内 `os.replace` / `NamedTemporaryFile` | ❌ 均正常 |

### 9.3 结论与采用的绕行方案

pip 的问题特定于**它自己创建的 `pip-unpack-*` / `pip-target-*` 目录**中的后续操作。精确机制未定位（pytest 写缓存时也复现过同样的 `WinError 5`，但 pytest 本身能跑完）。

**已验证可用的引导链（完全不经过 pip）**：

1. 用 Node 从 PyPI JSON API 下载 `uv` 的 Windows wheel —— `_tools/fetch_pypi_wheel.js`；
2. 用 Python `zipfile` 解压出 `uv.exe` —— `_tools/uv/uv-0.13.1.data/scripts/uv.exe`（31 MB，`uv 0.13.1`）；
3. 之后所有 Python 依赖统一交给 `uv pip install`，并把 `UV_CACHE_DIR` 指到工作区内。

> ⚠️ **必须写进 README**：否则任何人在这台机器上执行 `pip install -r requirements.txt` 都会撞墙。
